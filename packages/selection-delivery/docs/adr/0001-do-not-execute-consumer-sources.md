# 0001. 소비자의 원본을 실행하지 않는다

- 상태: Accepted
- 날짜: 2026-07-30
- 범위: selection

## 맥락

Selection & Delivery는 사용자 질의에 적합한 Context Card와 Retrieval Scope를 선택한다.
여기서 한 걸음 더 나가는 선택지가 있다. 선택된 테이블·컬럼으로 SQL을 생성해 실행하고,
API를 호출하고, 그 결과로 답변까지 만들어 주는 것이다.

대회 지정과제도 "질문에 답하는 AI 검색 비서"를 요구하므로 이 방향이 자연스러워 보인다.
그래서 안 하는 쪽이 의도적 결정임을 남긴다.

## 결정

PostgreSQL과 OpenAPI 소스에 대해서는 소비자가 실행할 **Retrieval Contract만** 반환한다.
테이블·컬럼·허용 연산, method·path까지의 검증 가능한 좌표가 이 도메인의 출력 경계다.

SQL 생성과 실행, HTTP 호출, 최종 답변 생성은 소비자의 책임이다.

## 기각한 대안

- **자연어 → SQL 생성 및 실행**: 조회 진입점을 하나 열면 커넥션 풀, read-only 트랜잭션
  경계, 쿼리 가드, 결과 절단, 에러 매핑, 권한 검사, 감사 로그가 전부 이 도메인의 책임으로
  들어온다. 프로토타입에서 실제로 확인한 목록이다. Selection은 검색 범위를 고르는 도메인이고,
  DB 프록시가 되는 순간 무엇을 보장하는지 말할 수 없게 된다.
- **답변 생성까지 수행**: LLM이 결정권자가 되는 지점이 늘어난다. 이 제품에서 판정은
  결정론적이어야 한다. 같은 입력이면 같은 판정이 나와야 하는데, 답변 생성을 품으면
  그 경계가 흐려진다.
- **지식그래프 구성 / 데이터 드리프트(로우 증가) 감지**: 필수 범위 밖이다.
  원본 - 청크 - 인덱스 - Card의 연결관계만 관리한다.

## 대가

- "질문에 답을 주지 않는다"가 기능 부재로 보인다. 이것이 미구현이 아니라 책임 제한을 위한
  설계 결정이라는 설명 부담을 문서와 데모가 진다.
- 소비자가 실행 계층을 직접 구현해야 한다. 따라서 Retrieval Contract가 그만큼 명확해야
  한다 — 좌표는 검증 가능해야 하고, 허용 연산이 명시되어야 한다.
